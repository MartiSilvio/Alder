The interpreter is Alder's default execution backend. It walks the bound tree node by node, evaluating each expression and propagating results through the tree. Every `BoundNodeKind` has a corresponding evaluator.

## Dispatch

The interpreter uses a per-node strategy pattern. Each node kind is handled by a dedicated static class in `Interpretation/Evaluators/`, annotated with `[EvaluatesNode(BoundNodeKind.Xxx)]`. There are 71 such evaluator classes. Dispatch from `BoundNodeKind` to the correct evaluator is source-generated by `EvaluatorDispatchGenerator` — the generated code is a flat switch expression mapping each node kind to its evaluator's static `Evaluate` method. No virtual method calls, no visitor pattern overhead.

## Fast Path vs Fallback

Binary and unary operators have a two-tier dispatch:

### Fast path (NumericDispatch)

When the binder has computed a `PromotedType` AND the runtime values' types match their static types, the engine routes directly to `NumericDispatch` — pre-built delegate tables keyed by `(Type, Type)` pairs:

```
Add: { (int,int)→(l,r)=>l+r, (long,long)→(l,r)=>l+r, (double,double)→(l,r)=>l+r, ... }
Subtract: { (int,int)→(l,r)=>l-r, ... }
Compare: { (int,int)→(l,r)=>l.CompareTo(r), ... }
```

This is how `1 + 2` evaluates without boxing, `dynamic`, or reflection. The binder pre-computes the promoted type (`int` for `int + int`), and the interpreter uses it as a direct table lookup key.

Checked arithmetic has separate delegate tables (`CheckedAddOps`, `CheckedSubtractOps`, `CheckedMultiplyOps`) that use `checked()` for integer types and standard operations for floating-point (per IEEE 754).

### Fallback path (Operators)

When types don't match the fast path (mixed types, nullables, `string + object`, `DateTime ± TimeSpan`, enum arithmetic, user-defined operators), the engine falls through to the general `Operators` class. This handles:

- String concatenation (any operand is `string`)
- `DateTime` arithmetic (`DateTime + TimeSpan`, `DateTime - DateTime`)
- Enum arithmetic (`Enum + int`, `Enum - Enum`, `~Enum`)
- Nullable three-valued logic (`bool? & bool?`, `bool? | bool?`)
- User-defined operators (`op_Addition`, `op_Subtraction`, etc.)
- Cross-type numeric promotion via `NumericDispatch.PromoteOperands`
- String repetition in Extended mode (`"ab" * 3`)
- Object merge in Extended mode (`new { A = 1 } + new { B = 2 }`)

Before entering the fallback path, `NumericPromotionRuntime.ApplyConstantNumericPromotion` handles ECMA-334 §10.2.11 — if one operand is a literal constant, it may be implicitly promoted (e.g., `int` 0 to `uint`).

## Control Flow

### ControlFlowSignal

Control flow uses a signal propagation pattern. `break`, `continue`, `return`, `goto`, `goto case`, and `goto default` produce `ControlFlowSignal` values that propagate upward through the evaluation stack:

| Signal | Produced by | Consumed by |
|--------|------------|-------------|
| `Return(value)` | `return expr;` | Engine entry point, lambda invocation |
| `Break` | `break;` | Innermost loop or switch |
| `Continue` | `continue;` | Innermost loop |
| `GotoCase(value)` | `goto case value;` | Switch statement |
| `GotoDefault` | `goto default;` | Switch statement |
| `Goto(label)` | `goto label;` | Block containing the target label |

Signals are NOT exceptions — they're ordinary return values of type `ControlFlowSignal`. Every intermediate construct (blocks, if-statements, try-catch) checks for signals and propagates them. Unwrapping happens at three boundaries:

1. **Engine entry point** (`AlderEngine.UnwrapControlFlowSignal`): Extracts the return value
2. **Lambda invocation** (`MethodInvoker.InvokeLambda`): Extracts the return value for the lambda's caller
3. **Compiled root** (`BoundExpressionEmitter.EmitUnwrapSignal`): Emits IL to extract the return value

### Loop Evaluation

Each loop creates a child context (`_context.CreateChild()`) for the iteration scope. The child context is cleared between iterations via `ClearScope()` — this is cheaper than creating a new context each time.

Loops check execution constraints on each iteration:
- `ExecutionRuntime.CheckExecutionConstraints` — statement count and timeout
- `ExecutionRuntime.CheckLoopIterationConstraint` — per-loop iteration count

The `_loopDepth` and `_breakContextDepth` counters track nesting for `break`/`continue` validation.

### Goto and Labels

`goto label` in a block produces a `Goto("label")` signal. The block evaluator handles it: when a goto signal is received, `FindLabelIndex` scans the statement list linearly for a `BoundLabelExpr` with the matching name, sets the execution index to the label position + 1, and re-enters the statement loop via a C# `goto ExecuteBlock` statement. This provides efficient intra-block jumps without creating new stack frames.

### Switch Statement Fall-Through and Goto Chaining

Switch cases enforce C#'s no-fall-through rule: if a case body executes without producing a control flow signal (break, return, throw, or goto), `CS0163: Control cannot fall through` is thrown. `goto case` and `goto default` inside switch cases produce signals that the switch evaluator resolves by scanning for the matching case pattern, then re-executing from that case in a loop — enabling multi-hop `goto case` chains without recursion.

### Try/Catch Signal Preservation

When a control flow signal (return, break, etc.) is encountered inside a `try` block, it is captured in `pendingSignal` rather than immediately propagated. The `finally` block always executes after the signal is captured. After `finally` completes, the pending signal is returned. This ensures that `return` inside `try` still executes `finally` — matching C# semantics exactly. If an exception occurs in `finally`, it supersedes both the pending signal and any caught exception.

### Pattern Matching (PatternRuntime)

The pattern matching runtime handles every ECMA-334 §11.2 pattern kind:

| Pattern | Algorithm |
|---------|-----------|
| Constant | Evaluates constant expression, then `Operators.Equals()` comparison (or `TypeHelpers.IsType()` if constant is a `Type` object) |
| Type | Resolves type, checks `is` instance, optionally binds variable with the resolved type |
| Var | Always matches, binds variable with runtime type (or `typeof(object)` for null) |
| Discard (`_`) | Always matches, no binding |
| Relational (`<`, `<=`, `>`, `>=`) | Evaluates operand, delegates to the corresponding `Operators` comparison method |
| And | Short-circuit: left first, right only if left matches |
| Or | Short-circuit: left first, right only if left fails |
| Not | Negates inner pattern result |
| Property (`{ Prop: pattern }`) | Optional type check, then for each property: `MemberAccess.GetMember` to read value, recursive match on subpattern. Short-circuits on first property mismatch. |
| Positional (`(p1, p2)`) | Checks `ITuple` interface, validates length, recursively matches each element |
| List (`[p1, p2, ..]`) | Gets collection length via `IList.Count` or `string.Length`. Without slice: exact length required. With slice: prefix + suffix patterns matched at edges, middle elements collected into array for slice subpattern. |
| Slice (`..`) | Matched within list patterns; captures the remaining elements between prefix and suffix |

Pattern variables are defined in the evaluation context at match time and are visible to `when` guards and subsequent code within the same scope.

## Method Invocation — Three-Tier Dispatch

Method calls use a three-tier dispatch architecture:

**Tier 1 — Typed dispatch (AOT-friendly, O(1)):** `TypedDispatchHelper.TryInvokeInstance` checks for source-generator-produced `ITypedDispatch` implementations. Uses a dictionary lookup keyed by type, walking the type hierarchy. No reflection.

**Tier 2 — Reflection with caching:** `OverloadResolver.TryResolve` selects the best overload. The resolved method is cached in `ResolutionCache` keyed by `(Type, methodName, ArgumentDescriptor[])`. Subsequent calls with the same argument shape hit the cache directly. Methods with 0–4 parameters that aren't on value types get a `FastInvoker` — a compiled delegate that bypasses `MethodInfo.Invoke`.

**Tier 3 — Extension methods:** Searched per-type in registration order. Each extension type is checked with interleaved typed dispatch (Tier 1) + reflection (Tier 2). Lambda arguments undergo return type inference: the engine evaluates the lambda body with the collection's element type as input, infers the return type, and converts the lambda to a concrete `Func<T, TResult>` delegate for overload selection.

**CancellationToken injection:** If any candidate method accepts `CancellationToken` as its last parameter and the caller provided one fewer argument than the parameter count, the engine automatically appends the current cancellation token to the argument list. This is transparent to expression authors.

**Callable type dispatch:** The unified `InvokeCall` entry point handles all callable types: `ModuleMethodRef` (dependency-injected module methods), `FunctionRef` (registered functions), `LambdaValue` (interpreted lambdas with closure capture), `CompiledLambdaValue` (pre-compiled lambdas with arity-specialized paths for 0–3 arguments), `Delegate` (standard .NET delegates via `DynamicInvoke`), `StaticMethodRef`, and `MethodRef`. Null produces `ALDR0302`; unknown types produce `NonCallableType`.

## Member Access

### Resolved member access

When the binder produced a `BoundPropertyAccessExpr` or `BoundFieldAccessExpr`, the interpreter has the `PropertyInfo`/`FieldInfo` and calls `GetValue` directly:

- Properties: `property.GetValue(target)` (with `TypedDispatchHelper` check first)
- Fields: `field.GetValue(target)` (with `TypedDispatchHelper` check first)
- Null-conditional (`?.`): If the target is null, returns null without accessing the member

### Dynamic member access

When the binder produced `BoundDynamicMemberAccessExpr`, the interpreter uses `MemberAccess.ResolveMember` which:
1. Checks typed dispatch via `TypedDispatchHelper` (`ITypedDispatch.TryGet`)
2. Checks `TypeMetadataProvider` cache for property/field
3. For `ExpandoObject`, reads from the `IDictionary<string, object?>` interface
4. Extended mode: checks `DateArithmeticSugar.TryResolveTimeSpanUnit` for numeric.days/hours/etc.

## Method Invocation

### Resolved calls

`BoundResolvedCallExpr` carries the selected `MethodInfo` from bind-time overload resolution. The interpreter:
1. Evaluates all arguments
2. Converts lambda arguments to delegates via `LambdaDelegateConverter`
3. Handles `out` parameters by creating wrapper variables
4. Invokes the method directly

### Dynamic calls

`BoundDynamicCallExpr` runs full runtime resolution:
1. Identifies the target (function, module method, instance method, extension method)
2. Runs overload resolution via `MethodInvoker`
3. Handles generic type inference for extension methods
4. Converts lambdas to delegates
5. Invokes the selected method

## AOT Integration

Before any reflection-based member access or method invocation, `TypedDispatchHelper` checks for typed dispatch:

```
if config.TryGetDispatch(type, out var dispatch)
    if dispatch.TryGet(name, instance, out var value)
        return value;
// fallback to reflection
```

The AOT check walks the type hierarchy — if dispatch exists for a base type, it's used. This means registering `[AlderRegistered(typeof(List<int>))]` covers access to members inherited from `IList<int>`, `ICollection<int>`, etc.

## Tracing

When `EvaluateWithTrace` is called, the interpreter receives an `EvaluationTracer`. Before each node evaluation, `_tracer.Push(expr)` records the node. After evaluation, `_tracer.Pop(result)` records the result. On error, `_tracer.PopError(exception)` records the failure.

The tracer builds a `TraceNode` tree that mirrors the evaluation order. The trace uses the security-only pipeline (no constant folding or dead branch elimination) so every node is visible.

## Context Management

The `_context` field on `BoundEvaluator` points to the current scope. It changes during evaluation:
- Block entry → `_context = _context.CreateChild()`
- Loop iteration → child context reused, cleared via `ClearScope()`
- `for` loop → two child contexts (initializer scope + body scope)

The engine saves and restores `_context` around scope changes using local variables, ensuring that scope exits always restore the previous context even on exceptions.

## Boxed Constants

Frequently-returned values (`true`, `false`, `0`, `1`, `null`) use pre-allocated boxed instances from `BoxedConstants` to avoid repeated boxing allocations on the hot path.
