# Executive verdict

This repository has real strengths: the binder-first architecture is visible in the code, the AOT story is not bolted on as an afterthought, the test suite actively guards architectural direction, and much of the runtime is trying to stay close to ECMA-334 and normal .NET behavior. The project does not feel careless.

It also still carries the weight of several cleanup phases layered on top of one another. The main risk is not one bad class. The risk is that too many important behaviors are now spread across overlapping dispatch paths, overlapping caches, and overlapping “fast path vs fallback” systems. The code often works by adding one more tier rather than removing an old tier.

The highest-leverage cleanup is not local polish. It is repository-wide consolidation of call resolution, dispatch, cache ownership, parser structure, and engine responsibilities.

# System mental model

The codebase is organized around this flow:

1. Parsing
   The parser is hand-written and split across `Lexer`, `ExpressionParser`, `PrimaryParser`, `StatementParser`, `PatternParser`, and `QueryParser`. Parsed syntax is represented in one large `Expr` hierarchy in [src/Alder/Parsing/Ast.cs](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Parsing/Ast.cs).

2. Binding
   The binder lowers syntax into typed bound nodes. `BindingContext` bridges binder-visible locals and runtime-visible variables. Binding services such as [CallBinderService](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Binding/Services/CallBinderService.cs) and [MemberBinderService](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Binding/Services/MemberBinderService.cs) do semantic resolution.

3. Runtime execution
   Interpreted execution uses `EvaluationContext` plus evaluator dispatch generated by `EvaluatorDispatchGenerator`. Runtime behavior then flows through large helper hubs such as [MethodInvoker](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/MethodInvoker.cs), [MemberAccess](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/MemberAccess.cs), [Operators](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/Operators.cs), `TypeHelpers`, and overload-resolution helpers.

4. Compiled execution
   The compiled backend emits expression trees through [BoundExpressionEmitter](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder.Compiled/Compilation/BoundExpressionEmitter.cs), `EmissionContext`, and many per-node emitters, backed by the giant [BoundRuntimeMethodCache](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder.Compiled/Compilation/BoundRuntimeMethodCache.cs).

5. AOT and source generation
   AOT dispatch is represented by [TypedDispatch](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Aot/TypedDispatch.cs) implementations generated by [AlderSourceGenerator](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder.Generators/AlderSourceGenerator.cs). Additional generators build bound-node rewriters, binder dispatch, emitter dispatch, and evaluator dispatch.

6. Public API and lifecycle
   [AlderEngine](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/AlderEngine.cs) is the public root and owns configuration building, context lifetime, parsing, evaluation, compilation, registration, tracing, some caches, and variable staging. [AlderEval](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/AlderEval.cs) is the global singleton surface.

# What is genuinely strong and worth preserving

- The binder remains the semantic authority in practice, not just in docs. `BindingContext`, `CallBinder`, `CallBinderService`, and the bound-node model consistently push type knowledge forward instead of rediscovering it later.
- The repository takes AOT seriously. AOT dispatch is a first-class system, not an optional convenience layer added at the edge.
- Architectural verification tests are unusually direct. [ArchitectureVerificationTests](/Users/silviomartignetti/Developer/Wovera/CsEval/tests/Alder.Test/Verification/ArchitectureVerificationTests.cs) shows active effort to remove wrapper churn and keep certain responsibilities centralized.
- Immutable read-mostly structures are used well in several places. `FixedDictionary`, frozen dictionaries, immutable arrays, and immutable config objects are good fits for the engine’s mostly read-heavy shape.
- Numeric semantics are explicit and deliberate. [NumericDispatch](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/NumericDispatch.cs) is large, but it is coherent, table-driven, and clearly trying to make operator behavior boring and predictable.
- The source generators are not ornamental. They remove real boilerplate in evaluator dispatch, binder dispatch, emitter dispatch, and AOT typed metadata.
- Tests reveal healthy paranoia about parity, cleanup regressions, and path equivalence across interpreted, compiled, and AOT modes.

# What still ages badly if left unchanged

- The call and dispatch stack is too layered. Binder-time resolution, runtime overload resolution, AOT typed dispatch, extension dispatch, resolved-call caches, argument preparation, compiled emitter direct-call emission, and canonical-name retries all overlap. This is the main long-term complexity sink.
- `AlderEngine` is too much of the system’s gravity well. It is split into partial files, but it is still one conceptual owner for too many unrelated responsibilities.
- The parser is still structurally monolithic even though it is file-split. Large manual lookahead rules in [ExpressionParser](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Parsing/ExpressionParser.cs), [PrimaryParser](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Parsing/PrimaryParser.cs), and [StatementParser](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Parsing/StatementParser.cs) will continue to harden into contributor-avoidance zones.
- The cache story is fragmented. There are many caches, several have custom eviction, several are static, and there is no obvious single policy for ownership, invalidation, or memory discipline.
- The compiled backend is effective but brittle. `BoundRuntimeMethodCache` is a giant string-and-signature-sensitive bridge between runtime internals and expression emitters. That works, but it is fragile and expensive to evolve.

# Where the repository carries artifacts of previous phases

- The tests explicitly enforce removal of older wrappers and symbol names. That is useful, but it also shows the codebase has repeatedly accumulated transitional layers and then needed cleanup policing.
- Names like `BoundRuntimeMethodCache`, `TryInvokeFast`, `PreferResolvedRuntimeDispatch`, `ResolutionCache`, `ExtensionDispatches`, and several “fallback” comments indicate a system that has grown by interleaving new dispatch tiers rather than collapsing old ones.
- `AlderEngine` partials reflect horizontal feature accretion more than a calm domain model.
- `AlderLinqExtensions` still uses `#region` sections and an overload zoo in one giant file, which feels like an API surface that expanded phase by phase.
- The existence of both [ExpressionTreeEmitter](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder.Compiled/Compilation/ExpressionTreeEmitter.cs) and [BoundExpressionEmitter](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder.Compiled/Compilation/BoundExpressionEmitter.cs) shows two compilation-oriented paths with different scopes and different unsupported-node boundaries.

# Where complexity is pretending to be sophistication

- The runtime call stack has too many “smart” layers:
  `CallBinderService` -> `OverloadResolver` -> `ApplicabilityChecker` -> `ArgumentPreparer` -> `MethodInvoker` -> `TypedDispatchHelper` -> `ResolutionCache` -> `ExtensionMethodResolver` -> compiled direct-call branches.
  Each piece is defensible alone. The system as a whole is now harder than it should be to reason about.

- [IteratorEnumerable](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/IteratorEnumerable.cs) creates a dedicated `Thread` plus two `SemaphoreSlim` instances per iterator enumerator. That is a large amount of machinery for “yield return” behavior. It may have been the easiest route at one point, but it will not age elegantly.

- [StructuralObjectTypeFactory](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/StructuralObjectTypeFactory.cs) emits runtime CLR types with `Reflection.Emit`. That is real machinery. It may be justified for some compiled/query scenarios, but as a general structural-object story it is heavy, upgrade-hostile, and difficult to simplify later.

- [BoundRuntimeMethodCache](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder.Compiled/Compilation/BoundRuntimeMethodCache.cs) centralizes compiled-runtime bridges, but it has become a giant dependency catalog. It does not feel elegant. It feels like technical necessity that was allowed to become a permanent shape.

- Case-insensitive AOT dispatch currently works by trying exact AOT dispatch, then reflecting to discover canonical member names, then retrying AOT with the canonical name in [TypedDispatchHelper](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/TypedDispatchHelper.cs). Functionally correct, but it is complexity added to patch a mismatch between the dispatch model and the engine surface.

# Where C# / .NET should replace hand-rolled machinery

- Iterator execution should use calmer .NET coordination primitives or a different iterator model rather than raw `Thread` management in `IteratorEnumerable`.
- `AlderLinqExtensions` should be generated or compressed around shared helper patterns instead of remaining a large hand-expanded extension surface in one file.
- The cache layers with manual queue-based trimming in [ResolutionCache](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/OverloadResolution/ResolutionCache.cs), [ExtensionMethodResolver](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/ExtensionMethodResolver.cs), and [TypeResolver](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/TypeResolver.cs) should be revisited. If those caches stay, they should likely share one calmer policy rather than three independent mini cache implementations.
- The parser should lean harder on reusable parse helpers and smaller syntax-form units. Right now too much behavior depends on handwritten token choreography spread across large files.
- Public API sprawl in `AlderEngine` and `AlderLinqExtensions` should be collapsed behind smaller service surfaces and standard delegation patterns rather than continuing as large manually maintained method sets.

# Deep cache skepticism audit

The repository contains many caches. Some are clearly justified. Many are not obviously unjustified, but the total system is too cache-happy to accept on trust.

Clearly justified or likely justified:

- `FixedDictionary` and frozen static tables for keywords, numeric operators, built-in names, and config snapshots.
- `TypeMetadataProvider` per-engine reflection lookup caches.
- `MethodDispatchCache` parameter and fast-invoker caches, assuming the fast path remains part of the architecture.

Questionable because of overlap or policy fragmentation:

- `AlderExpression._boundExpressionCacheByContext`
- `AlderEngine._pipelineCache`
- `ResolutionCache`
- `ExtensionMethodResolver.ResolvedCallCache`
- `TypeResolver._cache`
- `AlderEngine.VariableAccessorCache`
- `LambdaValue._bindingCache`
- `LambdaDelegateConverter.DelegateCache`
- `LambdaDelegateFactory.TaskMapperCache`
- `IteratorEnumerable.GenericMethodCache`
- `BoundRuntimeMethodCache` typed method caches

Main concerns:

- Multiple caches protect similar expensive paths without one obvious ownership boundary.
- Several caches are static and therefore process-lifetime, not engine-lifetime.
- Custom FIFO-ish eviction by `ConcurrentQueue` appears in more than one place. This is repeated infrastructure, not a calm shared policy.
- There is little visible evidence in the source that these caches are measured rather than inferred.
- Some caches may be compensating for repeated re-resolution that should itself be simplified.

The root problem is not any single cache. The root problem is that the repository uses caches as local pressure relief across many subsystems.

# Giant files, god classes, and ownership problems

Most concerning ownership concentrations:

- [AlderEngine](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/AlderEngine.cs)
  Even split across partials, it owns too much: config building, lifecycle, parsing entry, evaluation entry, compiled execution entry, tracing entry, variable staging, and internal cache placement.

  One file for the whole parsed node model is manageable early. At this size it hurts scanability and contributor confidence.

- [MethodInvoker](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/MethodInvoker.cs)
  This is a runtime hub. The issue is not that it is central. The issue is that too many dispatch concerns terminate here.

- [MemberAccess](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/MemberAccess.cs)
  This file mixes namespace resolution, module access, tuple behavior, typed dispatch, reflection fallback, index semantics, and language-mode sugar.

- [Operators](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/Operators.cs)
  Large and mixed. Some size is justified, but the file is carrying many special cases that deserve clearer sub-ownership.

- [BoundRuntimeMethodCache](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder.Compiled/Compilation/BoundRuntimeMethodCache.cs)
  This is a god-file of runtime method handles for the compiled backend.

- [AlderLinqExtensions](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder.Compiled/AlderLinqExtensions.cs)
  Very repetitive surface area, poor signal density, and not aligned with the repository’s otherwise stricter style.

# Patterns repeated across the repository that need cleanup

- Queue-trimmed concurrent caches with local max-size constants.
- “Try typed dispatch, then reflection fallback” in multiple forms.
- Case-sensitive/case-insensitive branching repeated across binder, runtime, and typed dispatch.
- Large manual switch dispatch systems plus generator-backed switch dispatch systems coexisting in adjacent layers.
- Repeated overload-surface expansion for convenience APIs.
- Split responsibilities where one subsystem partially resolves something and a later subsystem partially resolves it again.

# Contributor-hostile zones

- Parser lookahead logic in `ExpressionParser`, `PrimaryParser`, and `StatementParser`. This requires private context to change safely.
- Overload resolution and extension-method resolution in [OverloadResolver](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/OverloadResolution/OverloadResolver.cs), [ApplicabilityChecker](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/OverloadResolution/ApplicabilityChecker.cs), and [TypeInference](/Users/silviomartignetti/Developer/Wovera/CsEval/src/Alder/Runtime/OverloadResolution/TypeInference.cs).
- Compiled backend bridges centered on `BoundRuntimeMethodCache`, `EmissionContext`, and emitter classes.
- Source generators that depend on metadata names and internal shape conventions.
- `IteratorEnumerable` and `StructuralObjectTypeFactory`, because both involve runtime machinery that many contributors will avoid touching unless necessary.

# Performance realism concerns

- The repository has many caches and fast paths, but the strongest visible performance risk is actually complexity overhead and repeated resolution, not the absence of caching.
- `IteratorEnumerable` starts a real thread per enumerator. That is an obvious runtime cost with lifecycle complexity.
- `TypedDispatchHelper` case-insensitive canonicalization introduces reflection into the AOT path when the name case does not match.
- `TypeMetadataProvider.GetMethods` calls `RuntimeTypeIntrospection.GetMethods` and then filters by name. Depending on hot-path frequency, that may be acceptable, but it is still broad retrieval plus secondary filtering.
- `MemberAccess` and `MethodInvoker` do a lot of runtime shape branching. Some of this is unavoidable, but it means any additional special case has a system-wide cost.
- Large public helper surfaces like `AlderLinqExtensions` imply ongoing maintenance cost more than runtime cost, but the repeated helper layering also makes it harder to see the true hot paths.

# Upgrade-safety risks

- `BoundRuntimeMethodCache` is tightly coupled to internal runtime method names and signatures. This will make future runtime refactors more expensive than they should be.
- The source generators rely on metadata names and internal structural conventions. They are useful, but they reduce freedom to rename and reshape internals casually.
- `StructuralObjectTypeFactory` ties part of the system to runtime code generation. That is not a good long-horizon default if future AOT constraints expand.
- `AlderEval` enforces a single global engine configuration lifecycle. That is simple now, but rigid for more advanced host scenarios.
- `AlderConfig.TryGetDispatch` walks base types only. That is pragmatic, but it hardcodes part of dispatch inheritance behavior into the config surface itself.

# Top 12 repository-wide cleanup/refactor targets

1. Consolidate the call-resolution and dispatch stack
   Why it matters:
   The binder/runtime/compiled/AOT call path is the repository’s biggest complexity concentration.
   Why it matters in 10 years:
   Every new callable shape, conversion rule, or dispatch mode will keep multiplying work unless this is simplified.
   Likely subsystems/files involved:
   `CallBinder`, `CallBinderService`, `OverloadResolver`, `ApplicabilityChecker`, `ArgumentPreparer`, `MethodInvoker`, `TypedDispatchHelper`, `ExtensionMethodResolver`, compiled call emitters.
   Why it beats easier/local refactors:
   This is the root of multiple local complexities, multiple caches, and several contributor-hostile areas.

2. Split `AlderEngine` into explicit service owners
   Why it matters:
   The engine is too central and accumulates unrelated concerns.
   Why it matters in 10 years:
   A public root object with too much internal authority becomes the place every new feature leaks into.
   Likely subsystems/files involved:
   `AlderEngine.*`, `AlderConfig`, variable staging, parse/eval/compile/tracing entry points.
   Why it beats easier/local refactors:
   Local method cleanups will not change the ownership problem.

3. Re-architect the parser around smaller syntax ownership units
   Why it matters:
   Parser behavior is spread across several very large, tightly coupled hand-written files.
   Why it matters in 10 years:
   Syntax growth will become slower, riskier, and increasingly dependent on tribal knowledge.
   Likely subsystems/files involved:
   `ExpressionParser`, `PrimaryParser`, `StatementParser`, `PatternParser`, `QueryParser`, `Ast`.
   Why it beats easier/local refactors:
   The parser is a fundamental contributor interface. Reducing fear here has repo-wide value.

4. Collapse cache policy into a smaller number of owned caches
   Why it matters:
   The repository has too many ad hoc caches and custom mini-eviction strategies.
   Why it matters in 10 years:
   Memory behavior, invalidation bugs, and stale assumptions will get harder to reason about.
   Likely subsystems/files involved:
   `AlderExpression`, `AlderEngine`, `TypeResolver`, `ResolutionCache`, `ExtensionMethodResolver`, runtime delegate factories.
   Why it beats easier/local refactors:
   This addresses a systemic pattern, not one implementation detail.

5. Break up `BoundRuntimeMethodCache` and replace the giant static catalog with narrower capability surfaces
   Why it matters:
   The compiled backend is coupled to runtime internals through one oversized method-handle file.
   Why it matters in 10 years:
   This file will continue to calcify and make runtime cleanup expensive.
   Likely subsystems/files involved:
   `BoundRuntimeMethodCache`, `EmissionContext`, compiled emitters, runtime helper classes.
   Why it beats easier/local refactors:
   It improves upgrade safety across the compiled path.

6. Remove thread-per-iterator execution
   Why it matters:
   `IteratorEnumerable` is heavy machinery for language semantics that should feel ordinary.
   Why it matters in 10 years:
   Threading complexity ages badly and becomes a maintenance tax.
   Likely subsystems/files involved:
   `IteratorEnumerable`, lambda evaluation, yield handling, evaluator control flow.
   Why it beats easier/local refactors:
   This is both conceptual and runtime complexity, not style cleanup.

7. Revisit structural object runtime type generation
   Why it matters:
   `StructuralObjectTypeFactory` is sophisticated machinery with a high long-term cost.
   Why it matters in 10 years:
   Runtime codegen choices constrain AOT, portability, and internal simplicity.
   Likely subsystems/files involved:
   `StructuralObjectTypeFactory`, object-literal binding/runtime, compiled/query paths.
   Why it beats easier/local refactors:
   It removes one of the most advanced pieces of infrastructure in the repository.

8. Split `MemberAccess` into clearer subsystems
   Why it matters:
   Namespace resolution, module access, tuple behavior, typed dispatch, reflection fallback, and indexing should not all feel like one file’s responsibility.
   Why it matters in 10 years:
   Member access is on too many language paths to remain muddy.
   Likely subsystems/files involved:
   `MemberAccess`, member/index binders, typed dispatch helpers.
   Why it beats easier/local refactors:
   This is central runtime readability, not cosmetic cleanup.

9. Decompose `Operators` and clarify special-case ownership
   Why it matters:
   The operator surface is large and mixes numeric, enum, delegate, string, pattern, and extended-mode behavior.
   Why it matters in 10 years:
   Operator semantics will continue to grow edge cases, and this file will attract them all.
   Likely subsystems/files involved:
   `Operators`, `NumericDispatch`, enum helpers, comparison helpers.
   Why it beats easier/local refactors:
   It reduces a major semantic hub before it becomes worse.

10. Shrink and generate `AlderLinqExtensions`
   Why it matters:
   The file is repetitive, style-inconsistent with the repo, and high-maintenance for little conceptual value.
   Why it matters in 10 years:
   Public extension surface areas become permanent liabilities.
   Likely subsystems/files involved:
   `AlderLinqExtensions`, compiled parse helpers, public compiled API tests.
   Why it beats easier/local refactors:
   It improves public API maintainability and scanability immediately.

11. Break `Ast.cs` into syntax families
   Why it matters:
   One giant parsed-node file makes the syntax model harder to navigate than it needs to be.
   Why it matters in 10 years:
   Syntax models only get larger.
   Likely subsystems/files involved:
   `Ast.cs`, visitors, walkers, parser references.
   Why it beats easier/local refactors:
   It improves contributor orientation across the whole front end.

12. Reduce metadata-name string coupling inside generators
   Why it matters:
   The generators are powerful, but several rely heavily on metadata-name strings and structural assumptions.
   Why it matters in 10 years:
   Generator fragility becomes architectural drag when internal types evolve.
   Likely subsystems/files involved:
   `AlderSourceGenerator`, `BoundNodeGenerator`, `EvaluatorDispatchGenerator`, emitter/binder dispatch generators.
   Why it beats easier/local refactors:
   It improves internal evolvability rather than just current cleanliness.

# Top 3 targets to tackle first

1. Consolidate the call-resolution and dispatch stack
   This is the highest leverage because it sits at the intersection of binder complexity, runtime branching, compiled-path coupling, and cache growth.

2. Split `AlderEngine` into smaller service owners
   This is the fastest way to stop future complexity from flowing into the public root object.

3. Re-architect the parser around smaller syntax ownership units
   This is the best contributor-friendliness investment in the repository after dispatch consolidation.

# Final judgment

This is a strong repository with real architectural intent, not a mess. The problem is subtler than that. The codebase is at risk of becoming a very capable engine whose internal story is harder than it needs to be because every major cleanup has mostly centralized and layered complexity instead of deleting enough of it.

The repository does not need another neat local refactor. It needs a deliberate simplification campaign aimed at the major systems that now carry too much responsibility:

- invocation and dispatch
- engine ownership
- parser structure
- cache policy
- compiled-runtime coupling

If those are simplified with discipline, the project can become calm and durable. If they are not, the code will still work, but future contributors will increasingly treat the core as something to route around instead of something to confidently extend.
